# Lichess Multiplayer and Cloud Game Saves Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans or superpowers:subagent-driven-development to execute an approved plan. Steps use checkboxes for tracking.

**Goal.** Play online through Lichess and retrieve those matches across devices. Sync private solo history and resume an unfinished solo game across devices through the app's own account.

**Architecture.** Clients connect directly to Lichess for online play, reconnect and game history. Lichess holds the original online game records. For private solo saves, the app writes locally first and syncs versioned records to Firestore through authenticated JSON endpoints on the existing Fly.io Ktor service.

**Tech stack.** Kotlin Multiplatform, Compose, Ktor, kotlinx.serialization, Lichess Board and export APIs, OAuth 2.0 with S256 PKCE, russhwolf Settings, Firebase Auth REST, and Firestore Standard via the Firebase Java Admin SDK.

**Spec.** This consolidates the Nov 6 multiplayer and cloud-save requests. The proposed first release is a casual standard 15+10 challenge by Lichess username, with cross-device access to the Lichess archive. Follow with opt-in sync for finished solo games, then one active solo game per account.

## Where each game lives

| Game or data | Source of truth and recovery path |
| --- | --- |
| **Ongoing online match** | Lichess stores the moves, clocks, seats and result. After signing in on another device, discover the match through `/api/account/playing` and resume through the Board stream. [Ongoing games](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/games/api-account-playing.yaml), [Board game stream](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/board/api-board-game-stream-gameId.yaml) |
| **Finished online match** | Lichess already records the game. Read the user's history or export one game by ID. Keep an optional local PGN copy for offline access. Add Lichess bookmarks later if users want a separate list of selected games that follows their account. [User game export](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/games/api-games-user-username.yaml), [single-game export](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/games/game-export-gameId.yaml), [bookmark API](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/games/bookmark-gameId.yaml) |
| **Finished solo game** | The app owns the private history record, including PGN and move assessments. Lichess can store a PGN for review as a private Study chapter. Ordinary Lichess PGN imports are public. Treat a Study as an explicit export option if requested. Its chapter model and 64-chapter limit make it a poor fit for automatic app backup. [Public import](https://lichess.org/paste), [Study visibility](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/studies/api-study.yaml), [Study import](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/studies/api-study-studyId-import-pgn.yaml) |
| **In-progress solo game** | The app owns the versioned snapshot, player side, and revision that prevent one device from overwriting another's progress. A Lichess Study can preserve a line of play as PGN. It offers no app snapshot or revision contract for resuming the local Stockfish/CPU session. [Study chapter export](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/studies/api-study-studyId-chapterId.pgn.yaml) |

Tasks 1–4 ship online play and its archive using only Lichess sign-in. Tasks 5–7 add private solo sync with a separate, optional app account, so solo players can use it without a Lichess account. Both sources appear in History under their own labels. Local solo saves remain available offline.

## Global constraints

- Use each player's normal Lichess account with the `board:play` scope. Keep that authorization separate from the app's cloud save account.
- Keep the app's engine and AI features exclusive to solo play and solo game review. Multiplayer uses human moves, with PGN and replay available for finished matches. [Lichess Fair Play](https://lichess.org/page/fair-play)
- Send moves as explicit player actions. Take the displayed committed position and terminal result from the game stream. Treat clock interpolation as display state.
- Reuse the existing legal-move logic, 2D board and common 3D host. Keep changes out of the Filament renderers and Stockfish bridges.
- Leave rated play, variants, bots, premoves, chat and private app-owned rooms outside the first release. Start with the standard opening position.
- Support Android, iOS, Linux and macOS JVM desktop, and Wasm. Keep storage and network code outside `:chess-core`. Keep game state independent of the renderer.
- Keep solo play and the local Save game and Share PGN flows available without an account or connection. Use `SavedGame` and `GameSnapshot` as payloads with an explicit schema version. Include the player's side in the cloud resume envelope because that setting determines which side the engine plays.
- Cloud data belongs to a verified account. The Ktor server derives the owner from the Firebase ID token. Cloud credentials stay on Fly. Direct client access to Firestore is denied.
- Ship with separate switches for history sync and resume sync. Retain a local copy until the cloud acknowledges the write. Preserve manually saved games and deletes across offline restarts.
- Keep the AI corpus and retrieval dependency graph separate from cloud saves. Exercise the existing AI routes and monitor memory before enabling sync on the 512 MB deployment.

## AI and fair play

- **Human multiplayer uses the Board API.** Lichess prohibits external assistance in real-time human games, including casual challenges. Stockfish evaluation, generated move advice, position chat, opening guidance, books and tablebases are excluded during the game. The same rule applies whether assistance runs on the device or on Fly. The Board API can transmit a move selected by the player. [Lichess Fair Play](https://lichess.org/page/fair-play)
- **Bot play uses a separate account.** Lichess permits engine or AI-assisted play through the Bot API with a labeled `BOT` account. Only an account that has played zero games can be upgraded, and the upgrade is permanent. Bot accounts play through challenges and can face humans or other bots. The human side remains subject to the fair-play rules. Bot play is outside this release. [Lichess Fair Play](https://lichess.org/page/fair-play), [Board and Bot API comparison](https://lichess.org/@/lichess/blog/welcome-lichess-boards/XlRW5REA), [Bot account upgrade](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-account-upgrade.yaml)
- Gate assistance in the controller and in navigation. Cancel queued AI and engine evaluation requests on entering multiplayer. Keep assistance disabled while an unfinished match reconnects, including after an app restart. Once Lichess confirms a terminal result, players can view the result, replay the game on Lichess, export PGN, or return to solo play with their existing AI settings.
- Keep the Lichess source tag on archived games and local PGN copies. Check game source before starting assessment backfill, game summaries, opening explanations or other AI analysis from History. Only solo records are eligible.

## Multiplayer provider and connection

| Option | Fit for this app |
| --- | --- |
| **Lichess Board API, direct from the app** | Proposed. Provides human play, direct challenges and public seeks with regular accounts. It accepts UCI moves over HTTP and streams game state via NDJSON. The official browser demo shows client-only OAuth, seeks and gameplay. Supported time controls include rapid, classical and correspondence, plus blitz for direct challenges. | **Lichess via Fly** | A small OAuth callback helper could support a platform that needs a registered HTTPS return URI. A full relay adds token custody, long-lived connections, shared egress limits and another failure point. Revisit it if a direct client test exposes a specific blocker or if centralized token custody becomes a requirement. [Lichess API limits](https://lichess.org/page/api-tips), [Fly autostart and autostop](https://docs.fly.io/reference/fly-proxy-autostop-autostart) |
| **Other hosted chess servers** | Chess.com's public API supports archive access and provides no move-submission endpoint. FICS supports third-party clients over its legacy TCP/Telnet protocol. Browser support would require a separate compatible transport or relay. [Chess.com Published-Data API](https://www.chess.com/news/view/published-data-api), [FICS connection details](https://www.freechess.org/Help/HelpFiles/addresses.html) |
| **Run our own service** | Best fit if the goal is app-owned invite links or custom play rules. A small Ktor service could use `:chess-core` for move validation, persistent match records, server-owned clocks, a move endpoint, and a stream that sends a full state on reconnect. Avoid an in-memory-only match authority on a suspending service. Lila is available as open source but brings a Scala, MongoDB and separate WebSocket stack. A private instance would need its own players. [Fly autostop](https://docs.fly.io/reference/fly-proxy-autostop-autostart), [Lila architecture](https://github.com/lichess-org/lila) |

## Private solo storage options

The app uses `current_game.v1` for the single autosave and `game_history.v1` for up to 200 finished games that players save explicitly. `GameViewModel` writes snapshots through `GameSnapshotSink`, and the app reads the snapshot before constructing the VM. The Fly coach service is configured to suspend when idle and has no production database in its request path. See [CurrentGameStore](../../../app/src/commonMain/kotlin/com/example/myapplication/persistence/CurrentGameStore.kt), [GameHistory](../../../app/src/commonMain/kotlin/com/example/myapplication/persistence/GameHistory.kt), [game-over Save action](../../../app/src/commonMain/kotlin/com/example/myapplication/GameScreen.kt), [Fly configuration](../../../server/fly.toml), and [retired corpus database](../../../server/db/fly.toml).

| Option | Fit for this app |
| --- | --- |
| **Fly Ktor + Firestore** | Proposed. The existing multiplatform HTTP stack carries one app API. Firestore gives per-game documents, ordered queries and transactional writes without an always-on database VM. The published free allowance includes 1 GiB, 50,000 reads and 20,000 writes daily. Paid features include managed backups and restores. [Firestore quotas](https://firebase.google.com/docs/firestore/quotas) |
| **Direct Firebase** | Viable if the rollout starts with Android and iOS. For the full app, verify desktop and Wasm Auth and Firestore support per library and packaging target. Firestore REST works with Firebase ID tokens and owner rules. Native/browser SDK offline support differs, and ordinary offline writes to the same document use last-write-wins. [Firebase SDKs](https://firebase.google.com/docs/libraries), [GitLive SDK](https://github.com/GitLiveApp/firebase-kotlin-sdk), [REST auth](https://firebase.google.com/docs/firestore/use-rest-api), [offline behavior](https://firebase.google.com/docs/firestore/manage-data/enable-offline) |
| **Fly Ktor + Managed Postgres** | Strong option if we build our own live game service and need transactional player, invite and move records. The published Basic plan starts at $38/month plus storage. [Fly pricing](https://fly.io/docs/about/pricing/), [Managed Postgres](https://docs.fly.io/postgres) |
| **Fly Ktor + Tigris or a Fly Volume** | Tigris is a low-cost S3-compatible option for PGN or snapshot blobs and has conditional writes. Per-user history queries and multi-record operations would need additional design. SQLite on a Fly Volume could support a single-machine pilot and requires a restore plan for host failure because volumes are local to their hosts. [Fly Tigris integration](https://fly.io/hello/tigris/), [Tigris features](https://www.tigrisdata.com/features/), [Fly Volumes](https://docs.fly.io/volumes/overview) |

## Review focus

- A challenge accepted immediately still opens the match, and a canceled request cannot leave a surprise active seek.
- A move committed by Lichess whose HTTP acknowledgement is lost appears once after reconnection. The app holds input until it knows the authoritative position.
- A reconnect or takeback can supply a shorter or divergent move list. Rebuild the board and SAN from the server list without inventing a result.
- Black orientation, both castles, en passant and underpromotion survive replay. Castling notation in the provider's stream can differ from the app's internal UCI form.
- Timeout, resignation, abort and draw can end a game without changing the board. The displayed result and saved PGN use the server result. Finished multiplayer games remain eligible for replay and export.
- The same online match appears once even when it arrives from both the live session and the archive. A failed archive refresh keeps the previous view, and account switch hides the old view.
- A lost create acknowledgement followed by retry creates exactly one history entry.
- Legacy IDs are timestamp-based. Equal IDs with different PGNs import separately, while importing the same legacy entry twice yields the same cloud ID.
- Sign-out or account switch during a sync hides the former account's cached history and prevents its pending writes from replaying under the next account.
- Offline delete and reset survive relaunch and stale retries from another device.
- If a solo game is advanced on two devices, the app preserves both positions and asks which to resume before starting an engine move.
